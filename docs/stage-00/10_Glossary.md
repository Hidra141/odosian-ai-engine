# Purpose

This document defines the official terminology used throughout the ODOSIAN AI Engine.

All architecture documents, source code, prompts, documentation, and discussions should use these definitions consistently.

If a term is not defined here, it should not become an official project term until reviewed and added.

---

# General Terms

## AI Engine

The core system responsible for analyzing cybersecurity data, retrieving relevant knowledge, interacting with Large Language Models (LLMs), validating results, and producing structured outputs.

---

## Module

An independent software component with a well-defined responsibility and public interface.

Modules communicate only through approved interfaces.

---

## Pipeline

The ordered sequence of processing stages through which data flows from input to output.

---

## Workflow

The execution path followed by a request as it passes through the AI Engine.

---

# Rule Processing

## Detection Rule

A structured cybersecurity rule provided as input to the AI Engine.

Examples include Sigma rules, Elastic detection rules, or other supported rule formats.

---

## Rule Parser

The module responsible for parsing a detection rule into a structured internal representation.

---

## ParsedRule

The normalized object produced by the Rule Parser.

It contains the structured information extracted from the original rule.

---

# Entity Processing

## Entity

A meaningful cybersecurity object extracted from a rule or knowledge source.

Examples include:

- ATT&CK Technique
- CVE
- Process
- Command
- Registry Key
- File Path
- Domain
- IP Address
- User Account
- Service

---

## Entity Extraction

The process of identifying entities from structured or unstructured input.

---

## Entity Mapping

The process of converting extracted entities into canonical identifiers.

---

## Canonical Entity

The official normalized representation of an entity after alias resolution and normalization.

---

## Alias

An alternative representation of the same entity.

Example:

```
T1562
```

may resolve to a newer canonical technique depending on the mapping strategy.

---

# Knowledge System

## Knowledge Base (KB)

The collection of structured cybersecurity datasets used by the AI Engine.

The Knowledge Base stores factual information but does not perform reasoning.

---

## Knowledge Record

A single structured entry stored in the Knowledge Base.

---

## Knowledge Loader

The component responsible for loading datasets into the system.

---

## Knowledge Normalizer

The component responsible for converting raw records into a standardized internal format.

---

## Knowledge Repository

The interface used to query normalized knowledge records.

---

## Knowledge Graph (KG)

A graph representation of cybersecurity knowledge where entities are connected by meaningful relationships.

---

## Node

An individual entity within the Knowledge Graph.

---

## Edge

A relationship connecting two nodes in the Knowledge Graph.

---

# Retrieval

## Retrieval

The process of selecting relevant information from the Knowledge Base or Knowledge Graph.

---

## GraphRAG

A retrieval strategy that combines graph traversal with Retrieval-Augmented Generation (RAG) to provide richer contextual information to the LLM.

---

## Retrieved Context

The filtered information returned by the retrieval process for use in AI reasoning.

---

# Context

## Context

The complete collection of information provided to the LLM for inference.

Context may include:

- Parsed rule
- Extracted entities
- Knowledge records
- Graph information
- Instructions
- Prompt

---

## Context Builder

The module responsible for assembling the final LLM context.

---

# LLM

## LLM

Large Language Model used for reasoning and text generation.

---

## Provider

The implementation that exposes an LLM service.

Examples include cloud-hosted or locally deployed models.

---

## Prompt

A structured instruction sent to the LLM.

Prompts are maintained separately from application code.

---

## Prompt Template

A reusable prompt containing placeholders that are populated during execution.

---

# Validation

## Validation

The process of verifying that an AI response satisfies structural and quality requirements.

---

## Hallucination

Information generated by the LLM that is unsupported by the provided context or verified knowledge.

---

## Confidence

A measure indicating the reliability of a generated result according to the project's validation strategy.

---

# Output

## Response Formatter

The module responsible for converting validated AI output into the official API response format.

---

## Final Response

The validated and formatted result returned by the AI Engine.

---

# Project Terms

## Immutable Resource

A project resource that must never be modified during runtime.

Knowledge datasets are immutable resources.

---

## Configuration

External settings that control application behavior without modifying source code.

---

## Interface

A contract defining how one module communicates with another.

---

## Dependency

A required relationship where one component relies on another to perform its responsibilities.

---

## Single Responsibility

The principle that a module should have one primary responsibility and one reason to change.

---

# Maintenance Rules

- New terms must be reviewed before becoming official.
- Existing definitions should not be changed without architectural review.
- Documentation and source code should reference the terminology defined in this glossary.
- Deprecated terms should remain documented until fully removed from the project.
