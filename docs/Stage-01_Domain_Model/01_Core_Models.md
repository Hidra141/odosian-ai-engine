# Purpose

This document defines the core conceptual models used throughout the ODOSIAN AI Engine.

Core Models represent the primary business objects that flow through the system during rule analysis, knowledge retrieval, AI reasoning, validation, and response generation.

This document defines each model's purpose and responsibility without specifying implementation details, fields, or programming language constructs.

---

# Scope

This document covers:

- Core business models
- Model responsibilities
- Model lifecycle
- Model ownership
- Model relationships

This document does not define:

- Fields
- Data types
- Serialization
- Validation rules
- Python classes
- Database schemas

These topics are specified in later documents.

---

# Design Principles

Every Core Model should:

- Represent one business concept.
- Have a single responsibility.
- Be independent of implementation.
- Be reusable across modules.
- Support future extensibility.
- Avoid framework-specific dependencies.

---

# Core Models

## DetectionRule

### Purpose

Represents the original cybersecurity detection rule submitted to the AI Engine.

### Responsibilities

- Preserve the original input.
- Act as the starting point of the workflow.
- Remain immutable.

---

## ParsedRule

### Purpose

Represents the structured interpretation of a DetectionRule.

### Responsibilities

- Organize rule information.
- Normalize rule structure.
- Provide structured access for downstream processing.

---

## Entity

### Purpose

Represents a cybersecurity object discovered during analysis.

Examples include:

- ATT&CK Technique
- CVE
- Process
- Registry Key
- File
- Command
- Domain
- IP Address
- Service

---

## MappedEntity

### Purpose

Represents the canonical form of an Entity after normalization.

### Responsibilities

- Alias resolution.
- Canonical identification.
- Version mapping.

---

## KnowledgeRecord

### Purpose

Represents a single factual knowledge entry retrieved from the Knowledge Base.

### Responsibilities

- Preserve factual information.
- Remain immutable.
- Maintain source traceability.

---

## KnowledgePackage

### Purpose

Represents a collection of Knowledge Records relevant to the current request.

### Responsibilities

- Aggregate related knowledge.
- Preserve retrieval context.
- Support downstream reasoning.

---

## GraphNode

### Purpose

Represents an entity within the Knowledge Graph.

---

## GraphEdge

### Purpose

Represents a semantic relationship between two Graph Nodes.

---

## GraphContext

### Purpose

Represents contextual relationships discovered through graph traversal.

---

## RetrievedContext

### Purpose

Represents the filtered contextual evidence selected by GraphRAG.

### Responsibilities

- Rank evidence.
- Filter irrelevant information.
- Prepare supporting context.

---

## LLMContext

### Purpose

Represents the complete information package delivered to the language model.

### Responsibilities

- Combine all validated context.
- Prepare AI reasoning input.
- Preserve traceability.

---

## AIResponse

### Purpose

Represents the raw output generated by the language model.

This model has not yet been validated.

---

## ValidatedResponse

### Purpose

Represents an AIResponse that has successfully passed the Validation Engine.

### Responsibilities

- Guarantee structural correctness.
- Guarantee schema compliance.
- Ensure minimum quality requirements.

---

## FinalResponse

### Purpose

Represents the official response returned by the AI Engine.

This is the only response exposed outside the engine.

# Model Ownership

Every Core Model has:

- One clear responsibility.
- One producing module.
- Zero or more consuming modules.
- A well-defined lifecycle.

Ownership rules are defined in later documentation.

---

# Model Lifecycle

Core Models should:

- Be created by a single module.
- Remain immutable whenever practical.
- Never expose internal implementation details.
- Be replaced rather than modified during transformation.

---

# Future Extensions

The Core Model architecture supports:

- Additional rule formats.
- New entity categories.
- Multiple knowledge providers.
- Multiple graph implementations.
- Multiple LLM providers.
- Distributed processing.
- Multi-agent workflows.
